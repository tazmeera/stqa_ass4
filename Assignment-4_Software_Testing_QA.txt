Q1. What is a Defect? Explain the importance of defect tracking in
    software testing.
--------------------------------------------------------------------------
ANSWER:

A defect (also called a bug or fault) is a flaw in a software work product
(requirement, design, code or document) that causes the software to behave
differently from the expected or specified behaviour. When the faulty code
is executed, it may produce a failure that the user can observe.

Relationship: Error (human mistake) -> Defect (fault in the product)
-> Failure (wrong behaviour seen at run time).

Example: The requirement says "Transfer limit is Rs. 50,000 per day" but
the code allows Rs. 5,00,000. This is a defect.

Importance of defect tracking:
1. Visibility   - Everyone (testers, developers, managers) can see how many
                  defects exist and their current status.
2. Accountability - Each defect has an owner, so none are forgotten.
3. Prioritisation - Critical defects are fixed first based on severity and
                  priority.
4. Communication - A single, documented place for discussion between testers
                  and developers; avoids verbal misunderstandings.
5. Traceability  - Defects can be linked to test cases, requirements and
                  builds.
6. Metrics and analysis - Defect density, defect trends and root causes can
                  be calculated to improve the process.
7. Release decision - Open-defect counts support go/no-go decisions.
8. Reuse of knowledge - History of past defects helps avoid repeating them.

Q2. Explain the Defect Life Cycle with a suitable diagram.
--------------------------------------------------------------------------
ANSWER:

The Defect (Bug) Life Cycle is the set of states a defect passes through
from the moment it is found until it is closed.

DIAGRAM:

                        +-------+
                        |  NEW  |
                        +---+---+
                            |
                            v
                        +--------+  (reject / duplicate / not a bug)
                        |ASSIGNED|------------------+
                        +---+----+                  |
                            |                       v
                            v                  +----------+
                        +-------+  deferred    | REJECTED |
                        | OPEN  |-----------+  | /DUPLICATE|
                        +---+---+           |  +----+-----+
                            |               v       |
                            v          +----------+ |
                        +-------+      | DEFERRED | |
                        | FIXED |      +----------+ |
                        +---+---+                   |
                            |                       |
                            v                       |
                       +----------+                 |
                       |  RETEST  |                 |
                       +----+-----+                 |
              fails         |        passes         |
        +-------------------+--------------+        |
        v                                  v        |
   +----------+                        +--------+   |
   | REOPENED |--> back to ASSIGNED    | CLOSED |<--+
   +----------+                        +--------+

Flow in words:
1. Tester finds a defect and logs it -> NEW.
2. Test lead / defect manager reviews it and assigns it to a developer
   -> ASSIGNED.
3. Developer starts analysing -> OPEN.
4. Developer fixes it -> FIXED (or marks it Rejected / Duplicate / Deferred).
5. Fixed build goes to the tester -> RETEST (VERIFIED).
6. If the fix works -> CLOSED. If not -> REOPENED and returns to the developer.

Q3. What are the different states of a defect in the Defect Life Cycle?
    Explain each state.
--------------------------------------------------------------------------
ANSWER:

1. New        : The defect has just been found and logged by the tester. It
                is waiting for review.
2. Assigned   : The test/project lead has reviewed it, accepted it as valid
                and assigned it to a developer.
3. Open       : The developer has started analysing and working on the fix.
4. Fixed      : The developer has changed the code and resolved the defect;
                the fix is ready to be tested.
5. Pending Retest : The fix has been delivered in a new build and is waiting
                for the tester to verify it.
6. Retest     : The tester re-executes the failed test case(s) to confirm the
                fix.
7. Verified   : Retest passed; the defect is confirmed as fixed.
8. Closed     : The defect is finished; no more action is needed.
9. Reopened   : Retest failed or the defect reappeared; it goes back to the
                developer.
10. Rejected  : Developer/lead decides it is not a defect (works as designed).
11. Duplicate : The same defect was already reported; it is linked to the
                original one and closed.
12. Deferred  : A valid defect, but fixing is postponed to a later release as
                it is low priority.
13. Cannot Reproduce / Need More Info : Developer cannot recreate it; the
                tester is asked for more details.

Q4. Explain the process of Defect Tracking and Reporting in software
    testing.
--------------------------------------------------------------------------
ANSWER:

Defect tracking is monitoring a defect from discovery to closure; defect
reporting is communicating the defect details and status to stakeholders.

Process:
1. Discover   : Tester executes a test case and sees actual result differing
                from expected result.
2. Verify     : Tester re-runs to confirm it is reproducible and checks that
                it is not already reported (duplicate check).
3. Log        : Tester enters the defect in the tracking tool with all
                details (see Q5) plus screenshots/logs.
4. Triage     : Defect Review Board / lead checks validity, decides severity
                and priority, and assigns an owner.
5. Fix        : Developer reproduces, finds the root cause, fixes it, and
                updates the status with comments.
6. Retest     : Tester verifies the fix in the new build and also runs
                regression tests around the area.
7. Close/Reopen : Defect is closed if fixed; otherwise reopened.
8. Report     : Periodic reports (daily/weekly) are prepared: open vs closed
                defects, severity distribution, ageing, defect trend and
                module-wise defects. These are shared with the team and
                management.

Q5. What information should be included in a Defect Report? Explain.
--------------------------------------------------------------------------
ANSWER:

A good defect report is clear, complete, reproducible and objective.

1. Defect ID         : Unique identifier (e.g., BUG-1024) for tracking.
2. Title / Summary   : One-line description of the problem.
3. Project / Module  : Where the defect was found.
4. Build / Version   : Software version in which it was found.
5. Environment       : OS, browser, device, database, network, etc.
6. Description       : Detailed explanation of the problem.
7. Steps to Reproduce: Numbered steps so anyone can recreate it.
8. Expected Result   : What should have happened (as per requirement).
9. Actual Result     : What actually happened.
10. Severity         : Technical impact (Critical/Major/Minor/Trivial).
11. Priority         : Urgency of fixing (High/Medium/Low).
12. Status           : Current life-cycle state.
13. Reported by / Date : Tester name and date.
14. Assigned to      : Developer responsible.
15. Attachments      : Screenshots, videos, logs, test data.
16. Linked items     : Test case ID, requirement ID.
17. Comments / History : Discussion and status changes.

Example: "Login button not working on Chrome 120 when password contains '&'".

Q6. Differentiate between Defect Severity and Defect Priority with
    suitable examples.
--------------------------------------------------------------------------
ANSWER:

Severity = how serious the defect is for the system (technical impact).
Priority = how soon the defect should be fixed (business urgency).

+-------------------+--------------------------+--------------------------+
| Basis             | Severity                 | Priority                 |
+-------------------+--------------------------+--------------------------+
| Meaning           | Degree of impact on      | Order in which defect    |
|                   | functionality            | must be fixed            |
| Decided by        | Tester / QA              | Product owner / manager  |
| Based on          | Technical impact         | Business need, deadline  |
| Levels            | Critical, Major, Minor,  | High, Medium, Low        |
|                   | Trivial                  |                          |
| Changes           | Rarely                   | May change with schedule |
+-------------------+--------------------------+--------------------------+

Examples:
1. High severity, High priority : Payment gateway crashes on checkout.
2. High severity, Low priority  : App crashes only in a very rare, old
                                  browser nobody uses.
3. Low severity, High priority  : Company name misspelt on the home page
                                  (no functional impact, but embarrassing).
4. Low severity, Low priority   : Slight colour mismatch in an admin help
                                  page.

Q7. Explain the Defect Management Process in detail.
--------------------------------------------------------------------------
ANSWER:

Defect management is the systematic process of identifying, recording,
classifying, resolving and analysing defects to improve product quality.

Stages:
1. Defect Prevention   : Reduce chances of defects through reviews, standards,
                         training and root-cause analysis of past defects.
2. Defect Discovery    : Finding defects through reviews, static analysis and
                         test execution.
3. Defect Reporting    : Logging the defect with full information in a
                         tracking tool.
4. Defect Triage /
   Categorisation      : Validate, set severity/priority, assign owner.
5. Defect Resolution   : Developer analyses, fixes, and updates the status.
6. Verification        : Tester retests and runs regression tests.
7. Closure              : Defect is closed with proper comments.
8. Defect Analysis and
   Improvement         : Metrics (defect density, defect age, DRE) and root
                         causes are analysed; process improvements are
                         planned (lessons learned).

Roles: Tester (finds/verifies), Developer (fixes), Test Lead (triage),
Project Manager (decisions), Defect Review Board (disputes).

Q8. What are the main activities involved in Defect Management? Explain
    each activity.
--------------------------------------------------------------------------
ANSWER:

1. Defect Prevention    : Using checklists, reviews, coding standards and
                          lessons learned to avoid defects.
2. Defect Identification: Detecting deviations during reviews and testing.
3. Defect Logging       : Recording the defect with all details.
4. Defect Classification: Assigning type (functional, UI, performance,
                          security), severity and priority.
5. Defect Assignment    : Allocating defect to a developer with a target date.
6. Defect Resolution    : Root-cause analysis and code/document correction.
7. Defect Verification  : Retesting the fix and doing regression testing.
8. Defect Closure       : Closing the defect after successful verification.
9. Defect Tracking and Monitoring : Watching status, ageing, backlog.
10. Defect Reporting and Metrics  : Producing reports for management.
11. Process Improvement  : Using analysis results to improve future work.

Q9. Explain the role of Defect Management Tools in software testing.
--------------------------------------------------------------------------
ANSWER:

Defect management tools (e.g., JIRA, Bugzilla, Mantis, Redmine, Azure
DevOps, YouTrack) automate and organise defect handling.

Roles:
1. Central repository   : All defects stored in one place.
2. Workflow automation  : Enforces the life cycle and moves defects between
                          states and owners.
3. Collaboration        : Comments, attachments and notifications keep
                          testers and developers in sync, even if remote.
4. Traceability         : Links defects to requirements, test cases and
                          builds.
5. Search and filtering : Find defects by module, severity, status, etc.
6. Reports and dashboards: Automatic charts, trends and metrics.
7. Audit trail          : History of every change for accountability.
8. Integration          : Works with test management, CI/CD and version
                          control tools.
9. Saves time and reduces human error compared to spreadsheets or email.

Q11. Explain how defects are identified, recorded, assigned, fixed,
     retested, and closed during the Defect Management Process.
--------------------------------------------------------------------------
ANSWER:

Take an example: "Discount not applied for purchase of Rs. 5,000."

1. IDENTIFIED : While running test case TC-045, tester finds that expected
                10% discount is not applied (actual: 5%).
2. RECORDED   : Tester logs defect BUG-210 with steps, expected/actual
                result, environment, screenshot, severity = Major.
                Status = New.
3. ASSIGNED   : Test lead confirms it is valid, sets priority = High and
                assigns it to developer Ravi. Status = Assigned.
4. FIXED      : Ravi reproduces it, finds a wrong boundary condition
                (> 5000 instead of >= 5000), corrects the code, unit-tests
                it and marks Status = Fixed with comments and build number.
5. RETESTED   : In the next build, tester re-executes TC-045 with the same
                data and also runs related regression tests around the
                discount module.
6. CLOSED     : If the test passes, status = Verified/Closed with remarks.
                If it fails, status = Reopened and goes back to Ravi.

The history stays in the tool for later analysis.

Q12. What are Test Metrics? Explain their importance in software testing.
--------------------------------------------------------------------------
ANSWER:

Test metrics are quantitative measures that describe the progress, quality
and effectiveness of the testing process and the product under test.
Examples: number of test cases executed, pass percentage, defect density.

Importance:
1. Progress tracking     : Shows how much testing is complete.
2. Quality assessment    : Indicates product stability and readiness.
3. Decision making       : Supports release/no-release decisions.
4. Process improvement   : Reveals weak areas in the process.
5. Estimation / planning : Past metrics help estimate effort and time.
6. Team performance      : Measures productivity and effectiveness.
7. Risk identification   : Highlights risky modules (high defect counts).
8. Communication         : Gives objective data to stakeholders instead of
                           opinions.
9. Cost control          : Helps compare planned vs actual effort.

Q13. Explain different types of Test Metrics used to measure testing
     activities.
--------------------------------------------------------------------------
ANSWER:

A. Process Metrics (about the testing process)
   - Test case preparation productivity = test cases written / effort.
   - Test execution productivity = test cases executed / time.
   - Test coverage = requirements (or code) covered / total x 100.
   - Schedule variance, effort variance.
   - Defect Removal Efficiency (DRE).

B. Product Metrics (about the software)
   - Defect density = defects / size (KLOC or function points).
   - Defects by severity, module and type.
   - Mean time between failures (MTBF).
   - Pass/fail percentage.

C. Project Metrics
   - Planned vs actual effort and cost.
   - Test progress (S-curve).
   - Resource utilisation.

D. Common Formulas
   - % Test cases executed  = executed / total x 100
   - % Test cases passed    = passed / executed x 100
   - Defect detection rate  = defects found / test cases executed
   - Defect leakage         = defects found after release / (defects found
                              in testing + after release) x 100
   - Defect rejection ratio = rejected defects / total reported x 100
   - Defect age             = date closed - date opened

E. Absolute vs Derived: absolute metrics are raw counts (test cases written);
   derived metrics are calculated from them (percentages and ratios).

Q14. What is Test Reporting? Explain the importance of test reports in
     software testing.
--------------------------------------------------------------------------
ANSWER:

Test reporting is the process of collecting, analysing and presenting test
activity results and product quality information to stakeholders in a
structured document or dashboard.

Importance:
1. Gives a clear picture of testing progress and product quality.
2. Helps management decide on release readiness.
3. Communicates risks, open defects and limitations.
4. Provides evidence/proof of testing (audit and compliance).
5. Supports traceability from requirements to results.
6. Helps in planning corrective action and future improvement.
7. Builds client confidence through transparency.
8. Acts as a historical record for future projects.

Q15. What are the main contents of a Test Report? Explain.
--------------------------------------------------------------------------
ANSWER:

1. Report identifier and project details : Name, version, date, author.
2. Executive summary   : Short overview of results and recommendation.
3. Scope of testing    : What was and was not tested.
4. Test environment    : Hardware, OS, browsers, tools, test data.
5. Test approach       : Types of testing performed.
6. Test execution summary : Total, executed, passed, failed, blocked,
                          not run.
7. Defect summary      : Total, open, closed, by severity and module.
8. Test coverage       : Requirement and code coverage.
9. Metrics and charts  : Trend graphs, pass/fail pie chart.
10. Deviations from plan : Schedule or scope changes.
11. Risks and issues    : Unresolved problems, known limitations.
12. Exit criteria status: Whether criteria were met.
13. Recommendation / Sign-off : Go / No-go with approvals.
14. Appendices          : Detailed test results, defect logs.

Q16. Explain different Test Reporting Techniques used in software
     testing.
--------------------------------------------------------------------------
ANSWER:

1. Daily/Weekly Status Reports : Short summaries of progress, blockers.
2. Test Summary Report         : Final formal report at the end of a cycle.
3. Dashboards                  : Live, visual view (JIRA, TestRail,
                                 Grafana) updated automatically.
4. Charts and Graphs           : Pie chart (pass/fail), bar chart (defects by
                                 module), line chart (defect trend), burn-down.
5. Tabular reports             : Requirement Traceability Matrix, test
                                 execution tables.
6. Defect Reports              : Open/closed counts, ageing, severity
                                 distribution.
7. Verbal/Meeting reports      : Daily stand-ups, defect triage meetings.
8. Exception reporting         : Only highlights deviations and critical
                                 issues.
9. Automated reports           : Generated from CI/CD tools after each build.
10. Milestone reports          : Given at phase end (system test complete).

The technique is chosen depending on the audience (managers prefer summaries
and charts; developers prefer detailed defect logs).

Q18. Explain how defect metrics can be used to measure the quality of
     software.
--------------------------------------------------------------------------
ANSWER:

Defect metrics give objective evidence about product quality:

1. Defect Density = total defects / size (KLOC). Lower value means better
   quality. Compare modules to find weak ones.
2. Defect Distribution : By severity, module, type and phase. A large share
   of critical defects signals poor quality.
3. Defect Trend : Plot of defects found over time. A declining curve
   indicates stabilisation; a rising curve indicates problems.
4. Defect Removal Efficiency (DRE) = defects found before release /
   (found before + after release) x 100. Higher DRE = better quality.
5. Defect Leakage : Defects reaching production show testing gaps.
6. Defect Age : Long-open defects indicate slow resolution/backlog.
7. Open vs Closed ratio : Shows readiness for release.
8. Reopen rate : High rate indicates poor fixing quality.
9. Mean Time To Detect / Fix : Indicates response efficiency.

Example: Module A has 40 defects in 10 KLOC (4 per KLOC) and Module B has
5 in 10 KLOC (0.5 per KLOC), so Module A needs extra testing and review.

Q19. Explain how Test Metrics can be used to measure the effectiveness
     and efficiency of a testing team.
--------------------------------------------------------------------------
ANSWER:

Effectiveness = doing the right thing (finding defects, meeting objectives).
Efficiency    = doing it with minimum time, cost and effort.

Effectiveness metrics:
- Defect Detection Percentage (DDP) = defects found by testing / total
  defects x 100.
- Defect leakage to production (lower is better).
- Requirement and code coverage.
- Percentage of valid defects (low rejection ratio).
- Test case effectiveness = defects found / test cases executed.

Efficiency metrics:
- Test execution rate (tests per person per day).
- Test design productivity (test cases written per person-day).
- Effort variance = (actual - planned) / planned x 100.
- Schedule variance.
- Cost per defect found.
- Automation percentage and rework (reopened defects).

Example: Team A executes 50 tests/day and finds 95% of defects; Team B runs
30 tests/day and finds 80%. Team A is both more efficient and more effective.
Metrics should be used to improve, not to blame individuals.

Q20. How can metrics be used to identify problems and improve testing
     effectiveness? Explain.
--------------------------------------------------------------------------
ANSWER:

Steps for using metrics to improve:
1. Collect data from test and defect management tools.
2. Compare against plan/benchmarks to find gaps.
3. Analyse the cause and decide an action.

Problem -> Metric signal -> Improvement action:
- Many defects in production  -> High defect leakage
     -> Add test cases for missed scenarios, increase regression coverage.
- Low coverage                -> Coverage metric below target
     -> Add test cases for uncovered requirements/code.
- Many rejected defects       -> High rejection ratio
     -> Improve requirement understanding and defect report quality.
- Delays                      -> Schedule/effort variance
     -> Re-plan, add resources, automate.
- Defects concentrated in modules -> Defect clustering
     -> Focus more testing/review on those modules.
- Many reopened defects       -> High reopen rate
     -> Better developer unit testing, improved retest procedure.
- Slow fixes                  -> High defect age
     -> Improve triage and communication.
- Late defect detection       -> Defects found mostly in later phases
     -> Introduce early reviews and static testing (shift-left).

Metrics should be tracked for each release and the trend reviewed to confirm
the improvements are working (continuous improvement, PDCA cycle).
